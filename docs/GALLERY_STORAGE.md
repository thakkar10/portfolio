# Client gallery photo storage

Decision for the first implementation: **Cloudinary authenticated image assets for files, MongoDB for gallery records.** This uses infrastructure already configured in the portfolio and keeps private originals and display derivatives out of ordinary public Cloudinary URLs.

## Upload path

1. An authenticated photographer chooses multiple JPEG, PNG, or WebP files (up to 100 MB per file in this first slice).
2. The app creates a draft gallery in MongoDB. Each file receives a unique Cloudinary public ID under `client-galleries/<gallery-id>/` and a short-lived upload signature generated by the server.
3. The browser uploads each file directly to Cloudinary as delivery type `authenticated`, with at most three transfers running at once. This avoids sending large image bodies through the Next.js server.
4. The server verifies the returned Cloudinary asset ID, resource type, delivery type, and gallery folder before adding a media record to MongoDB.
5. MongoDB stores the title, status, access settings, cover choice, focal point, ordering, sets, filenames, dimensions, and Cloudinary identifiers. It does **not** store image bytes.

Cloudinary confirms that an `authenticated` asset requires signed access for both its original and transformed versions: https://cloudinary.com/documentation/control_access_to_media. Its signed browser upload pattern is documented at https://cloudinary.com/documentation/client_side_uploading.

## Client delivery

- Gallery metadata and image requests check publication state and the gallery password session on the server.
- Display images use constrained Cloudinary transformations (900px grid, 2200px viewer) fetched through the app's gallery image route. The browser does not receive a reusable signed Cloudinary display URL.
- When downloads are enabled, a single-photo request creates a Cloudinary time-limited original download URL (60 seconds).
- Private galleries do not return media IDs or image URLs before access. Password hashes live in MongoDB; only an HTTP-only gallery cookie records access.
- Favorite selections live in their own MongoDB collection. Each list has a random 256-bit recovery token; only its SHA-256 hash is stored. A client can copy a private selection link to reopen the list on another device, subject to the gallery password. Anyone who receives that link can act on the list until it is submitted, so it should be shared privately.
- Demo pages use sample Unsplash images and do not upload or store anything.

## Cost and scale tradeoff

Cloudinary stores the originals and produces display variants. MongoDB stores small metadata records. Because the app currently relays display image bytes to enforce access without Cloudinary's premium token/cookie controls, **the app host also pays bandwidth for viewed images**. This is appropriate for the first gallery slice and should be measured with real gallery sizes before broad rollout. Cloudinary documents token and cookie access as premium features, and notes that its time-limited download API is not suitable for embedding routine display images: https://cloudinary.com/documentation/control_access_to_media.

If gallery traffic or storage volume becomes large, evaluate object storage (for example S3-compatible storage) plus a private image CDN, or Cloudinary's token-based delivery, against actual monthly media and bandwidth usage. No migration is needed to review the current gallery experience.

Existing Bunny Stream integration remains the likely path for gallery videos; this first slice handles photos only.

## Current limitations

- Bulk ZIP downloads, video gallery uploads, email-verified identity, and download activity reporting are not implemented yet.
- Admin design preview at `/admin/galleries?demo=1` and client design preview at `/g/demo` contain only sample images.
- Production builds currently depend on Google Fonts through the portfolio root layout. In network-restricted environments, the build can fail at font fetching before compilation completes.
